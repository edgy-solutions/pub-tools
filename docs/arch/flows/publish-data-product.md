# Publishing a data product (FL-PT-PUBLISH)

This flow follows one PUB LOG table from the public source to its entry in the catalog and its route in the mesh. It asks what starts the work, where the bytes land, how the table gets its one identity, and what a reader is handed when it asks for the table. It crosses four components here, [CO-PT-PIPELINE](../components/publog-pipeline.md), [CO-PT-LAKE](../components/lake-library.md), [CO-PT-CATALOG](../components/catalog-wiring.md) and [CO-PT-IMAGE](../components/pub-tools-image.md), which runs the broker (dag-tools CO-BROKER), and four dag-tools records: CO-DAGSTER, CO-MINIO, CO-DATAHUB and CO-GATEWAY.

The flow has two halves that do not wait for each other. The run and the catalog sensor publish the table's data and its catalog entry. The broker advertises a route to the table when its pod starts, whether or not the table has been written. The gateway's half of a read, and the access decision, are a dag-tools record (dag-tools FL-NTK) and are not repeated here.

**This record describes; it proposes nothing.** Statuses are those of [the README](../README.md), and line numbers are at the pins listed there. The record shape is provisional.

## Findings

1. **A run starts from a schedule or by hand, and nothing else starts one.** There is no sensor on the source and no event from it. The source's `Last-Modified` is read only inside a run, by the staging step. `built`
2. **The bytes pass through the pod twice and are held on its disk once.** The archive is downloaded to a temporary directory, and its members are streamed to the store in chunks; Python handles those bytes, line by line where it repairs an encoding fault. The conversion then reads the staged CSV from the store and writes Parquet back to it inside DuckDB, so no rows pass through Python there. `built`
3. **The table has one identity, spelled the same in four places.** The asset key holds the store's instance, the bucket and the path. The IO manager writes to the path that key names. The catalog sensor names the dataset from the key and the platform the step declared. The broker names its route from the key and the platform on its ticket. A dag-tools test pins the agreement between the sensor's name and the broker's. `built`
4. **The catalog entry follows the run; the route does not.** The sensor registers a table after a run materializes it. The broker registers routes for every asset the code location can materialize, when its pod starts and every two minutes after, so a route can exist for a table that has never been written. A read of such a table gets a ticket that points at nothing. `built`
5. **The staging step has a catalog entry too, and lineage joins it to its tables.** The staging step declares the object-store platform and its undated prefix, so its entry is the staged dataset rather than a Dagster-only entity. Each table asset depends on its staging asset, and the sensor records that dependency as lineage. `built`
6. **A reader is handed the producer's write credentials.** At the pinned dag-tools, the ticket the broker returns is the one the IO manager built, and it contains the key pair pub-tools writes with ([CO-PT-IMAGE](../components/pub-tools-image.md), finding 5). `built` at the pin; every dag-tools release from v0.3.0 changes it (dag-tools ADR-0044, commit `c198373`), and pub-tools has not moved.
7. **A skipped run publishes again, without new data.** When nothing changed, both steps skip, and each still emits a materialization carrying its declared platform. The sensor sees a materialization and re-registers the same entry under the same name; the catalog gains a run but not a second dataset. `built`

## Gaps

- **Present exposure: readers receive write credentials** (finding 6; step 16). Replacing them with a credential minted per read is `not built` at the pin. dag-tools tracks it as its roadmap row 3 (dag-tools issue #72).
- **Present exposure: route registration and resolution are unauthenticated** (steps 14 to 16). Any caller that reaches the broker can resolve a table: the broker at the pin has no guard on resolve, which is `not built`. Any caller that reaches the deployed gateway can replace a name's route: the gateway the chart deploys (0.14.0) has a guard on registration, but the chart leaves its posture unset, which means observe, so an unauthenticated registration is logged and served. That guard is `built` and not enforced; the broker at the pin sends no service token for it. Enforcing it depends on pub-tools PR #8 (the pin moves to dag-tools v0.17.0, whose broker presents a token and guards resolve; `proposed`; it stays a draft until Lane 1 shows that role assumption works for a regular store user, and the chart pieces are in a release, per the architect's ruling of 2026-11-19) and on chart settings that are `not built`; [CO-PT-IMAGE](../components/pub-tools-image.md) lists all five.
- **Present exposure: the catalog entry is written with no credential when the token is absent** (step 12). Requiring the token is `not built`.
- **A route can point at a table that does not exist yet** (finding 4). Nothing checks that a route's table has been written. `not built`
- **The sensor-and-broker agreement is tested in dag-tools, not here.** No pub-tools test builds a pub-tools asset's name both ways. `not built`
- **A failed step is not retried** ([CO-PT-PIPELINE](../components/publog-pipeline.md), finding 3), so the catalog entry and the data stay at the last good run until the next run. `not built`

## Not established from code

- Whether the schedules are running in a given deployment, so whether step 1 happens without an operator.
- Whether the catalog service requires a token in a given deployment, so whether step 12 succeeds there.
- Whether the broker's registration with the gateway succeeds in a given deployment (step 14).
- How long after a run the sensor registers it; that depends on the sensor's interval and the deployment's daemon, and no run was recorded.
